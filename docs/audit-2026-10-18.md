# Repository audit and safe refactoring

## Scope and rollback

Audit started from `ee1abe4` on 2026-10-18. Work is on `audit/safe-refactor-20261018`. Initial tracked edits and the untracked preparation layout test were copied byte-for-byte under ignored `data/audit-checkpoint-20261018/`, alongside a binary Git patch. The initial preparation screen already includes the previous small optimization. That work and the user's preparation design are preserved. No record files, SQL migrations, dependencies, or public command formats are being removed or upgraded.

## Previous refactor

The previous change replaced repeated student-name searches with a per-render Map, appended to new local groups instead of copying them, and calculated the preparation date once per render. These are valid local improvements. The empty-name fallback also masked a missing-student error; the screen still assumes the student exists when rendering. It was insufficient evidence for a repository-wide conclusion: no baseline performance comparison, full ESLint run, browser test run, dependency graph, or broad subsystem review was completed.

## Verification and results

The existing preservation-sensitive command rules, SQL migrations, package dependency versions, and data formats remain in place. No removal of compatibility code, dependencies, assets or historical validation evidence was justified. The previous preparation optimization and user's stylesheet/layout test remain byte-for-byte unchanged during this follow-up.

### Applied phases

1. **Date conversion and occupancy.** Reuse at most sixteen timezone date formatters (no records or formatted date results are retained), construct timestamp-part formatters once per conversion, and avoid duplicate Home filtering. Occupancy parses each visit once, uses a Set for selected dates, and searches chronological hour segments for actual overlaps. A differential check against `ee1abe4` matched all 96 generated cases across four timezones, DST months, weekday gaps, duplicate visit IDs and crossing intervals. The source aggregates were unchanged.
2. **Snapshot consistency and planners.** `/api/state` returns its synchronized transaction result rather than loading the aggregate a second time. Local and mocked-cloud tests verify committed revisions and no-op behavior. Temporary repeat settings copy only their object path; frozen-aggregate tests protect saved history and packet identities.
3. **Shared chart grouping.** `calendar-buckets.ts` replaces duplicated duration/homework calendar traversal. Binary assignment avoids rescanning the entire history per bucket. Source order, empty intervals, clipped calendar edges, leap days and the 3,700-bucket guard are retained. Duration averages and packet-weighted homework totals remain independent.
4. **Client work.** Conditional screens load through Next's documented dynamic-import pattern. Center Activity is separate from Progress; `v3-charts.tsx` retains compatibility exports. Header/elapsed clocks update their own components, date-based charts update on center-day changes, and live occupancy keeps its own second-by-second clock. No CSS or visual redesign was introduced. A dedicated browser regression checks midnight rollover, elapsed minutes and occupancy before the next snapshot poll.
5. **Development reliability.** Pin Corepack's documented pnpm version; exclude runtime/test artifacts from TypeScript and editor watchers; provide `pnpm benchmark`. Browser runs use new fictional data paths and preserve previous runs. Tests now wait for asynchronous confirmation, distinguish already-confirmed subjects, use PAPER subjects for physical-packet checks, support weekdays/weekends, and check packet-group alignment while permitting individual chips to wrap. Outdated Quick View/preparation documentation now reflects current behavior.
6. **Approved persistence safety fix.** Narrow the missing-file catch to the initial read without changing schemas, migration steps or successful-load behavior. Eight new isolated tests cover one-time backup/write/rename failures for both supported migration sources, recovery on retry, missing-file initialization and initial read permission failure. The preservation checks include IDs, visit timestamps, observation content, reviewer attribution, original audit events, expected migration steps and revisions, plus unchanged backup bytes. Existing-backup `EEXIST` handling, locking and atomic replacement remain intact. This phase changes error handling only; no performance gain is claimed for it.

### Measurements

These are local samples on the same Windows machine, not a controlled laboratory or device compatibility claim. The in-memory workload warms once and takes five samples per case. Browser measurements use Chrome, the same 2,110-visit fictional file, three fresh browser contexts, CDP metrics, and a five-second idle window after Home → Center Activity. The initial browser baseline overlapped other browser testing, so navigation/HTTP/memory comparisons have additional noise. The deterministic CPU workload is the stronger comparison.

Build speed did not improve in these samples; the compiler portion was 476 → 493 ms. An earlier first build after changing chunk boundaries took 15.69 s. Browser heap after forced GC was about 19.8–27.7 MB before and 11.75 MB after; server RSS samples were about 201–283 MB before and 271–334 MB after. These short samples do not establish a leak or a server memory improvement. The backend still serializes and sends the complete staff aggregate.

### Remaining work and limits

1. Snapshot size and complete-aggregate local serialization grow with history. Pagination, persistence decomposition or changed API payloads require a separate approved design and workload study.
2. Profile history repeatedly matches historical visits, academic plotting has a quadratic per-level scan, and skill point grouping can repeat work on interaction. The academic plot was about 1 ms on the measured fixture, so it was not rewritten. Larger histories deserve targeted profiling before further changes.
3. Long Quick View/command handlers and additive CSS overrides remain maintenance concerns, not evidence by themselves of slow execution. Changes there need focused domain and visual acceptance criteria.
4. Supabase Auth/RLS/tenant isolation, live recovery, real-device camera behavior, provider dictation approval, long-running memory behavior, and external dependency security advisories were not validated in this local audit. No real records or live database migrations were used.
